# RedPiano Mod — Deep Architecture & Version-Porting Guide

> **Audience:** any future agent who must (a) develop the RedPiano Fabric mod
> further, or (b) **port it to a different Minecraft version**. Porting is the
> user's explicit priority, so the version-sensitive surface is enumerated
> exhaustively in §6.
>
> **Scope:** documentation only. This file describes the mod **as it exists on
> disk** (MC 1.21.8 / Fabric / Mojang official mappings). It does **not** modify
> mod source. Where it recommends changes (e.g. a missing gradle wrapper, a
> version-range strategy), those are *proposals* for a future agent to apply.
>
> **All file:line references** below point at the real tree under
> `mod/redpiano/`. Code excerpts are verbatim.

## 0. What the mod is, in one paragraph

RedPiano is a tiny server-side Fabric mod (1 entrypoint + 1 mixin + 1 static
map, ~250 LOC total) that **re-skins the vanilla note block**. When a real
`minecraft:note_block` is triggered by redstone, the mod looks at the block
**directly below it** ("the mapping block"); if that block is in a 103-entry
lookup table, it cancels vanilla's 16-instrument sound and instead plays a
**custom high-quality sampled instrument** (piano / bass / lead / pad / drums
from the `qzpno` resource pack) at the note block's exact pitch. Crucially, it
plays that sound **once per online player, centered on each player** — which is
the fix that made the music sound "perfect" regardless of where the listener
walks. Everything else about the note block (particles, redstone mechanics,
visuals) stays vanilla. That is the entire mod.

The mod is **Family A** in this project's taxonomy (note-block re-performance).
It is the only machine family that requires a mod; Families B and C are
datapack/resourcepack-only and do not touch this code.

## 2. Architecture & data flow

### 2.1 The end-to-end path of a single note

```
redstone pulse rises on a note block
        │
        ▼
NoteBlock.triggerEvent(state, level, pos, id, param)   ← vanilla method, server side
        │   (Fabric mixin @At("HEAD"), cancellable)
        ▼
NoteBlockMixin.redpiano$customSound(...)
        │   1. e = RedPianoMap.lookup( level.getBlockState(pos.below()).getBlock() )
        │   2. if e == null  → return (let vanilla play its 16 instruments)
        │   3. note  = state.getValue(NoteBlock.NOTE)            (0..24)
        │      pitch = NoteBlock.getPitchFromNote(note)          (force transpose)
        │   4. spawn ParticleTypes.NOTE  (real note-block visual kept)
        │   5. holder = SoundEvent.createVariableRangeEvent(e.sound)
        │   6. if (level instanceof ServerLevel):
        │          seed = pos.asLong()*31 + level.getGameTime()
        │          RedPiano.QUEUE.add( new Pending(holder, e.volume, pitch, seed) )
        │   7. cir.setReturnValue(true)   ← cancel vanilla, event handled
        ▼
        … (more note blocks may fire on the same tick, each appends to QUEUE) …
        ▼
ServerTickEvents.END_SERVER_TICK  →  RedPiano.flush(server)     ← once, at tick end
        │   n = QUEUE.size()
        │   polyGain = (poly on && n>1) ? 1/sqrt(n) : 1     ← equal-power chord mix
        │   for each Pending q:
        │       vol/pitch humanized from q.seed (±3 cents, ±2% vol) if human on
        │       for each online ServerPlayer p:
        │           p.level().playSeededSound(null, p, q.sound,
        │                       SoundSource.RECORDS, vol, pitch, 0L)   ← centered on p
        │   QUEUE.clear()
        ▼
every player hears every note centered on themselves — distance-independent
```

### 2.2 Why "mapping block + note-block re-skin" instead of a custom block

The design re-uses the **real `minecraft:note_block`** and only reads the block
*below* it to choose the timbre. Consequences (all intentional):

- **100% vanilla note-block mechanics.** Redstone wiring, the visual model, the
  note-particle, instrument-by-block-below (vanilla already keys timbre off the
  block under the note block) all keep working. The mod only *expands* the
  "block-below → timbre" table from vanilla's hardcoded 16 to an arbitrary 103.
- **No block/item registration.** Nothing new is registered — no `Block`, no
  `BlockItem`, no `BlockEntity`, no model/blockstate JSON. That is why the only
  asset in the jar is a one-line `lang` file, and why the mixin is the entire
  behavioural surface. This dramatically shrinks the version-porting surface:
  **registration code is usually the most version-fragile part of a mod, and
  this mod has none of it.**
- **Pitch is forced.** Vanilla does *not* transpose custom sound events
  (only its own 16). The mixin calls `NoteBlock.getPitchFromNote(note)` itself
  (`NoteBlockMixin.java:32`) so our samples obey the note block's note value.

### 2.3 Why queue-then-flush (not play immediately)

`NoteBlockMixin` does **not** play sound inline. It appends a `Pending` to a
static queue (`NoteBlockMixin.java:40`) and `RedPiano.flush` drains it at
`END_SERVER_TICK` (`RedPiano.java:36`). Reason: the polyphony gain `1/sqrt(N)`
needs **N = how many notes fired this whole tick** (a chord), which is only
known once the tick is over. Per-note immediate playback could not compute it.

## 3. The mixin — exhaustively (this is the #1 cross-version breakage point)

File: `mod/redpiano/src/main/java/com/redpiano/mixin/NoteBlockMixin.java`

```java
@Mixin(NoteBlock.class)                                                  // :24
public class NoteBlockMixin {
    @Inject(method = "triggerEvent", at = @At("HEAD"), cancellable = true) // :26
    private void redpiano$customSound(BlockState state, Level level, BlockPos pos, int id, int param,
                                      CallbackInfoReturnable<Boolean> cir) {        // :27-28
        RedPianoMap.Entry e = RedPianoMap.lookup(level.getBlockState(pos.below()).getBlock()); // :29
        if (e == null) return;                                            // :30  non-mapped → vanilla
        int note = state.getValue(NoteBlock.NOTE);                        // :31
        float pitch = NoteBlock.getPitchFromNote(note);                   // :32  force transpose
        level.addParticle(ParticleTypes.NOTE, ... note / 24.0, 0.0, 0.0); // :33-34 real note particle
        Holder<SoundEvent> holder =
            Holder.direct(SoundEvent.createVariableRangeEvent(ResourceLocation.parse(e.sound))); // :35
        if (level instanceof ServerLevel) {                               // :38  server-only
            long seed = pos.asLong() * 31L + level.getGameTime();         // :39  deterministic seed
            RedPiano.QUEUE.add(new RedPiano.Pending(holder, e.volume, pitch, seed)); // :40
        }
        cir.setReturnValue(true);                                         // :42  cancel vanilla
    }
}
```

**Target (the version-sensitive contract):**

| Aspect | Current value (1.21.8, Mojang mappings) | Why it can break across versions |
|---|---|---|
| Target class | `net.minecraft.world.level.block.NoteBlock` | Class package/name is **Mojang-mapping-specific**. Under Yarn it is `net.minecraft.block.NoteBlock`; under Intermediary it's an obfuscated `net.minecraft.class_####`. Switching the mappings used in `build.gradle` changes every type name in this file. |
| Target method | `triggerEvent` | This is the **Mojang-mapped name**. Yarn calls it `onSyncedBlockEvent`. The method exists to handle block events (note blocks use a block event to play their sound). Mojang has renamed/refactored block-event methods before; **verify the method name and that it is still the note-block's sound entry point every version.** |
| Descriptor / params | `(BlockState state, Level level, BlockPos pos, int id, int param)` returning `boolean` | Mixin matches by name **and** descriptor when overloaded. If Mojang changes the signature (e.g. adds a param, or `Level`→`ServerLevel`), the `@Inject` silently fails to apply. Because `redpiano.mixins.json` sets `"defaultRequire": 1`, a failed apply throws at load (good — fail loud, not silent). |
| Injection point | `@At("HEAD")`, `cancellable = true` | HEAD is the most stable injection point (no reliance on internal instructions). `cancellable` + `cir.setReturnValue(true)` is how we suppress vanilla. Keep HEAD; avoid `INVOKE`/`FIELD` targets that bind to internal bytecode. |
| Callback type | `CallbackInfoReturnable<Boolean>` | Must match the method's `boolean` return. If the return type changes across versions, this type changes too. |

**Vanilla API calls used inside the mixin (each is a porting checkpoint):**

- `state.getValue(NoteBlock.NOTE)` (`:31`) — the `IntegerProperty NOTE`. Property
  field name/location can move; verify `NoteBlock.NOTE` still exists.
- `NoteBlock.getPitchFromNote(int)` (`:32`) — static pitch helper; Mojang name.
  Under Yarn this is `NoteBlock.getNotePitch(int)`. **Verify it stays static and
  takes the 0..24 note int.**
- `level.addParticle(ParticleTypes.NOTE, x, y, z, dx, dy, dz)` (`:33`) — particle
  overload + `ParticleTypes.NOTE` enum-like field.
- `SoundEvent.createVariableRangeEvent(ResourceLocation)` (`:35`) — factory for a
  variable-range (non-fixed-distance) sound event. Name has changed historically
  (`of`/`createVariableRangeEvent`). See §4 note on overloads.
- `Holder.direct(...)` (`:35`) — wraps a `SoundEvent` in a `Holder`. The
  `playSeededSound` overload we use (§4) wants a `Holder<SoundEvent>`.
- `ResourceLocation.parse(String)` (`:35`) — Mojang name; Yarn `Identifier.of`/
  `tryParse`. Parses e.g. `"qzpno:pno_c4_mf"`.
- `pos.asLong()` (`:39`) and `level.getGameTime()` (`:39`) — for the seed.
- `level instanceof ServerLevel` (`:38`) — server gate; **critical**, because
  the actual playback (§4) is server-driven per-player.

If a port produces silence with no crash, the **first** suspect is that the
`@Inject` did not apply (wrong method name/descriptor for the new version). With
`defaultRequire: 1` that should crash at load instead; if someone lowered that,
re-raise it.

## 4. Sound internals — the "perfect audio" fix and the overload root cause

File: `mod/redpiano/src/main/java/com/redpiano/RedPiano.java`

### 4.1 The flush loop

```java
private void flush(MinecraftServer server) {                       // :40
    if (QUEUE.isEmpty()) return;
    int n = QUEUE.size();                                          // :42
    int poly = readCfg(server, "poly", 1);                        // :43  0=off, else on
    boolean human = readCfg(server, "human", 1) != 0;             // :44
    float polyGain = (poly != 0 && n > 1) ? (float)(1.0/Math.sqrt(n)) : 1.0f;  // :45
    List<ServerPlayer> players = server.getPlayerList().getPlayers();          // :46
    for (Pending q : QUEUE) {
        float vol = q.volume() * polyGain;                        // :48
        float pitch = q.pitch();
        if (human) {                                              // :50
            Random r = new Random(q.seed());
            pitch *= (float)Math.pow(2.0, (r.nextDouble()*2-1) * 3.0/1200.0);  // :52 ±3 cents
            vol   *= (float)(1.0 + (r.nextDouble()*2-1) * 0.02);              // :53 ±2% vol
        }
        for (ServerPlayer p : players) {                          // :55
            p.level().playSeededSound(null, p, q.sound(),
                    SoundSource.RECORDS, vol, pitch, 0L);         // :58  centered on player
        }
    }
    QUEUE.clear();                                                // :61
}
```

### 4.2 `playSeededSound(null, p, sound, RECORDS, vol, pitch, 0L)` — the camera/earshot fix

This is **the line that made the music "perfect"** (memory:
*redstone-music-camera-and-earshot*). The historic problem: a note block plays a
positional sound at the block's world coordinate; if the listener walks away
(or rides past in a marching machine), they **leave the sound's audible sphere**
and the music cuts out. Teleporting the camera did **not** fix it.

The fix: emit the sound **per player, with the player entity as the source
position** (`playSeededSound(player=null /*everyone*/, entity=p, ...)` — the
2nd arg `p` is the *entity the sound is centered on*). Because the sound rides
each player, **every player is always at the centre of every note**, so the
sound is distance-independent: never cut, never quality-degraded, whether the
player stands still, walks, or follows a moving machine. Standing still is
audibly identical to before, so this is a strict superset.

**Overload note (porting):** Mojang has several `playSeededSound`/`playSound`
overloads. The one used here is the `(Player except, Entity centerEntity,
Holder<SoundEvent>, SoundSource, float vol, float pitch, long seed)` form. When
porting, confirm an overload with that exact shape still exists — Mojang has
both `(…, double x, double y, double z, …)` (positional) and the entity-centered
form, and the parameter that is `null` here is "the player to exclude" (null =
play for everyone). Getting the overload wrong is a common silent mis-port
(wrong arg meaning → sound at wrong place or not heard).

### 4.3 `SoundSource.RECORDS` — why this channel, not `MASTER`/`MUSIC`

`SoundSource.RECORDS` (`:58`) is deliberate (memory:
*redpiano-runtime-gotchas*):

- It is the **jukebox/record channel**, which is **not** subject to the
  music-volume ducking / one-track-at-a-time behaviour of `MUSIC`, and is louder
  and more reliable for sustained playback than ambient channels.
- **Consequence for stopping notes:** because notes play on RECORDS, you
  **cannot** silence the melody with a plain `/stopsound @a master …`. The
  melody-cut path (used by the generators for sustain-cut) must target the
  **RECORDS source** and the **specific event id** — i.e. `stopsound @a record
  <event>`. This is exactly why `gen_multi_map.py` records the full event id
  (`qzpno:…`) per block (see §5), so the datapack can issue precise
  `stopsound` cuts. Do not "simplify" RECORDS to MASTER — it breaks both the
  no-duck behaviour and the cut path.

### 4.4 Polyphony gain `1/sqrt(N)` — the "audio drop = server overload" root cause

When a chord fires, N samples play simultaneously. Naïve summation clips
("削顶", peak-clipping). `polyGain = 1/sqrt(N)` (`:45`) is **equal-power**
mixing: total energy stays roughly constant as N grows, so chords don't blow the
mix. N is the count of notes **this tick**, which is why queue-then-flush exists
(§2.3).

This ties to the historic **"audio drop = server overload"** finding (memory:
*redpiano-runtime-gotchas*, round 5): the real audio dropouts were the **server
being overloaded** (too many simultaneous note events / a sprawling machine),
not a mixing bug. The fix there was a **compact machine**; the `1/sqrt(N)` gain
is the *mixing-side* complement that keeps dense chords clean. When porting,
keep both in mind: if audio drops after a port, profile server tick time before
blaming the mixer.

### 4.5 Humanize (`±3 cents` / `±2%`) and determinism

`human` on (`:50`) applies a tiny pitch jitter (±3 cents, **below the
just-noticeable-difference**, so it doesn't sound out of tune) and ±2% volume
jitter, to remove the "bit-for-bit photocopy" feel of identical repeated
samples. It is **deterministic**: seeded by `pos.asLong()*31 + gameTime`
(`NoteBlockMixin.java:39`), so the same note at the same place/time always
jitters identically (reproducible, not random crackle).

### 4.6 `rpcfg` scoreboard runtime switches

`readCfg` (`RedPiano.java:65-71`) reads a scoreboard objective named **`rpcfg`**;
the fake-player rows `poly` and `human` toggle the two features (non-zero/absent
= on; explicit 0 = off). This lets a command block / datapack flip behaviour at
runtime with no rebuild:

```
scoreboard objectives add rpcfg dummy
scoreboard players set poly  rpcfg 0   # disable polyphony gain
scoreboard players set human rpcfg 0   # disable humanize
```

Absent objective or absent score → the `def` argument (1 = on). Porting note:
the scoreboard API (`getScoreboard`, `getObjective`, `getPlayerScoreInfo`,
`ScoreHolder.forNameOnly`, `ReadOnlyScoreInfo.value`) changed shape in the
1.20.x→1.21 era (the `ReadOnlyScoreInfo`/`ScoreHolder` types are relatively
recent). If porting **backwards** below 1.21, this block needs the older
`Score`-object API.

## 5. The 103-block / 5-instrument map

### 5.1 Structure (`RedPianoMap.java`)

`RedPianoMap` (`:11`) is a `final` class holding a static
`Map<Block, Entry>` (`:18`) where `Entry = (String sound, float volume)`
(`:12-16`). Populated in a `static {}` block with **103** `MAP.put(Blocks.X,
new Entry("qzpno:…", V f))` lines (`:20-122`). Lookup is a single
`MAP.get(block)` (`:125`). Layout of the 103:

| Instrument | Sound-id prefix | Count | Block palette (examples) | Base volume(s) |
|---|---|---|---|---|
| Piano | `qzpno:pno_*` | 60 | concrete / terracotta / wool / stone family (`WHITE_CONCRETE …`) | 1.4 / 1.7 / 2.0 (p/mf/f dynamic layers) |
| Bass | `qzpno:bass_*_mf` | 9 | glazed terracotta (white..light_gray) | 2.2 |
| Lead | `qzpno:lead_*_mf` | 18 | glazed terracotta (cyan..) + all `*_PLANKS` | 1.9 |
| Pad | `qzpno:pad_*_mf` | 16 | mangrove..warped planks + cobble/stone-brick/polished family | 1.5 |
| Drums | `qzpno:drum_*_x` | 5 | deepslate-tiles / cobbled-deepslate / blackstone family | 2.6 |

Total = 60+9+18+16+5 = **103**. (Vanilla has 16, hardcoded; this is "任意大".)

### 5.2 Single source of truth + the round-trip

```
poc/samples_manifest_*.json  ──(gen_redpiano_map.py)──►  RedPianoMap.java  (in the jar)
                                                              │
                                                              │  (gen_multi_map.py parses it back)
                                                              ▼
                                              poc/redpiano_map_multi.json
                                                              │
                                                              ▼
                          consumed by poc/46,47,48,49 generators (block choice, vol, stopsound id)
```

- `RedPianoMap.java` is the **canonical** mapping: it is what actually runs in
  game. Header comment (`:9`, `:99-100`) says *generated by `gen_redpiano_map.py`,
  do not hand-edit*. (Minor doc bug: `RedPianoMap.java:9` credits
  `gen_redpiano_map.py` — correct — but an older comment string elsewhere says
  `gen_redpiano_map.py 生成`; both refer to the same writer. The *reader* is
  `gen_multi_map.py`. Do not confuse the two.)
- `gen_multi_map.py` (`poc/gen_multi_map.py`) **re-parses the Java** with a
  regex and emits `redpiano_map_multi.json` so the Python generators never
  hand-copy the table and **stay byte-consistent with the jar**.

### 5.3 How `gen_multi_map.py` extracts it (and where it's brittle)

The extraction regex (`gen_multi_map.py:20`):

```python
pat = re.compile(r'MAP\.put\(Blocks\.(\w+),\s*new Entry\("qzpno:([a-z0-9_]+)",\s*([\d.]+)f\)\)')
```

It then splits each sound id by `_`: `toks[0]` = instrument; for pitched
instruments `toks[1]`=note, `toks[2]`=layer; for drums `'_'.join(toks[1:-1])`=
type and the trailing `_x` is dropped. `note_to_midi` (`:14-16`) converts e.g.
`c1→24`, `a5→81`.

> **KNOWN ISSUE #1 — brittle regex (audit-flagged).** The parser is a single
> regex over Java source text, not a real parse. It hard-assumes:
> - the literal `MAP.put(Blocks.NAME, new Entry("qzpno:…", N.Nf))` shape on one
>   line, no line breaks, `f` suffix present;
> - the **`qzpno:`** namespace literally;
> - sound ids matching `[a-z0-9_]+` and the `instr_note_layer` / `drum_type_x`
>   token grammar.
>
> Any of: reformatting the generated Java, renaming the namespace, an
> instrument whose id has a different token count, or a volume written as an
> integer (`2f` not `2.0f`) → **the entry is silently dropped** from the JSON
> with no error (the regex just doesn't match). The only guard is the final
> `total mapped blocks … (should = 103)` print (`gen_multi_map.py:83-84`) — it
> **prints** the count but does **not assert** it. **Recommendation:** turn that
> into an assertion, and prefer regenerating `RedPianoMap.java` via
> `gen_redpiano_map.py` over editing it, so the shape the regex expects is
> guaranteed.

> **KNOWN ISSUE #2 — two incompatible drum mappings (audit-flagged).** The same
> 5 drum blocks are keyed **two different ways** by the two generators, and the
> instrument is even named differently:
>
> | | writer | instrument name | drum key space | example keys |
> |---|---|---|---|---|
> | `redpiano_map.json` | `gen_redpiano_map.py` | **`drums`** (plural), `kind:"perc"` | **raw sample base-MIDI** | `"36","38","42","45","49"` |
> | `redpiano_map_multi.json` | `gen_multi_map.py` | **`drum`** (singular) | **type name** + separate `gm_drum_map` | `"kick","snare","hihat_closed","tom","crash"` |
>
> So `redpiano_map.json` says drum block ↔ `base_midi 36`, while
> `redpiano_map_multi.json` says drum block ↔ type `kick`, **plus** a GM table
> `gm_drum_map` (`gen_multi_map.py:67-72`) mapping many GM percussion notes
> (35,36→kick; 38,40,37→snare; 42,44,46,54→hihat_closed; …) onto those 5 types.
> The Python generators (`46/47/48/49`) consume **only the multi map**
> (`GDRUM = MM['gm_drum_map']`, e.g. `poc/46_build_inplace_multi.py:43`), so the
> `drums`-keyed `redpiano_map.json` is effectively legacy/unused for drums.
> **Risk:** if a future agent wires anything to `redpiano_map.json`'s drum keys,
> or assumes the two files agree, drums will map wrong. Treat
> `redpiano_map_multi.json` (+`gm_drum_map`) as authoritative for drums and
> consider deleting/regenerating the `drums` block of `redpiano_map.json`, or
> unifying both writers on the type-name + `gm_drum_map` scheme.

`gen_multi_map.py` also emits `family_map` (`:48-65`, GM `program//8` 0..15 →
sample set pno/bass/lead/pad/drum) — the auto "by GM family" instrument choice.

## 6. *** VERSION-PORTING GUIDE *** (core deliverable)

Goal: adapt the mod to a **new Minecraft version** with confidence. The surface
is small (no registrations), and breakages cluster in **two files**
(`build.gradle`, `NoteBlockMixin.java`) plus three config files. Work top-down.

### 6.0 Pre-flight: pin the exact toolchain numbers

Before touching code, gather these four numbers for the target MC version (all
from official sources):

1. **Yarn/Mojang mappings** build for the target MC (we use Mojang official —
   `loom.officialMojangMappings()`).
2. **fabric-loader** version compatible with target MC.
3. **fabric-api** version: the `…+<mcversion>` build (e.g. `0.136.1+1.21.8`).
4. **fabric-loom** plugin version that supports the target MC + your Gradle/JDK.

Sources: <https://fabricmc.net/develop/> (one page lists loader/api/yarn/loom for
each MC version), and <https://minecraft.wiki/w/Pack_format> for §6.4.

### 6.1 Version-sensitive surface — the master checklist

| # | Thing | Where it lives (file:line) | How to update | How to verify |
|---|---|---|---|---|

### 6.2 Step-by-step port procedure

1. **Pin numbers** (§6.0). Edit `build.gradle:2,19-22` and the dep ranges in
   `fabric.mod.json:15-20`.
2. **Choose mappings.** Staying on Mojang official keeps all the
   `net.minecraft.*` names in `RedPiano.java`/`NoteBlockMixin.java` valid as-is.
   Switching to Yarn means renaming every imported type and the method
   (`triggerEvent`→`onSyncedBlockEvent`, `getPitchFromNote`→`getNotePitch`).
   Prefer staying on Mojang official.
3. **Re-resolve the mixin target (the crux).** Open the target version's
   `NoteBlock` in your dev environment (Loom genSources) and confirm:
   - the method that fires the note-block sound (still `triggerEvent` under
     Mojang) and its **exact signature**;
   - `NoteBlock.NOTE` and `getPitchFromNote(int)` still present.
   Update `NoteBlockMixin.java:26-27,31,32` only if signatures changed.
4. **Re-resolve sound APIs.** Confirm `SoundEvent.createVariableRangeEvent`,
   `Holder.direct`, the `playSeededSound` entity-centered overload, and
   `SoundSource.RECORDS` (`RedPiano.java:58`, `NoteBlockMixin.java:35`).
5. **Compat levels.** Set `redpiano.mixins.json:5` and the `java` ranges to the
   target JDK.
6. **`pack_format` / folders.** This is **not in the mod** — it lives in
   `redpiano_core.py`'s `VERSION_TABLE`. Add/confirm the target row (§6.4).
7. **Build** (§6.3) and **smoke-test in game** (§6.6).

### 6.3 The exact build command (Windows, current setup)

There is **no checked-in gradle wrapper** (see §6.5), so builds use a
locally-installed Gradle distribution. From memory (`redpiano-mod-build-command`),
the working invocation is:

```bash
# JDK 21 is required (java >=21).
export JAVA_HOME="<path-to-your-jdk-21>"   # e.g. .../jdk-21.0.11+10

# NOTE the wrapper-path quirk: the local Gradle has an EXTRA gradle-9.2.1/ level,
# i.e. the gradle.bat is nested one directory deeper than expected. Use the
# fully-qualified path to that gradle.bat (do not assume ./gradlew exists).
#   …/gradle-9.2.1/gradle-9.2.1/bin/gradle.bat   ← the doubled level

cd mod/redpiano
"<path>/gradle-9.2.1/gradle-9.2.1/bin/gradle.bat" build
```

- **Jar output:** `mod/redpiano/build/libs/redpiano-1.0.0.jar`
  (version from `build.gradle:6`; current on-disk jar is ~11.6 KB, mtime
  2026‑06‑22). **Verify the jar's mtime/size changed** after a build to be sure
  it actually recompiled — a no-op build leaves the old jar.
- **Changing the jar requires a Minecraft restart, NOT `/reload`.**
  `/reload` only reloads datapacks/resourcepacks; mod classes are loaded once at
  JVM start. After replacing the jar in `mods/`, fully restart the client/server.

### 6.4 `pack_format` lives in Python, not the mod (§17–19 of the checklist)

The mod jar contains **no** `pack.mcmeta` and is version-range-gated only by
`fabric.mod.json`. The **datapack** and **resourcepack** `pack_format` numbers —
which DO change every MC version — are owned exclusively by
`scripts/redpiano_core.py`:

- `VERSION_TABLE` (built by `_vrow`, `redpiano_core.py:86-122`) maps each
  `mc_version` to a **rich record** — `dp_format, rp_format, function_folder,
  packmeta_shape, sign_dialect, has_tick_rate, has_return_cmd, tier, confidence,
  notes` (plus `tps`/`game_ticks_per_cell` surfaced on the profile). Anchored row:
  `"1.21.8": _vrow(81, 64, "function", "single", "component_snbt", True, "green",
  "high", …)` (`:117-118`) — dp=81, rp=64, **singular** `function/`, single
  `pack_format`, SNBT sign dialect. Rows span **1.20..1.21.9**.
- `get_version_profile(mc_version)` (`:165-193`) is the **only** accessor; it
  **raises** on an unknown version (never guesses) and on any version below the
  `/tick rate` floor (`has_tick_rate==False`, ≤1.20.2). `assert_build_supported`
  (`:196-…`) then enforces the green band (1.21..1.21.9), refusing the "yellow"
  1.20.3..1.20.6 rows (datapack adapts but the mod needs a `<1.21` source-port).
  Nothing else may hardcode a `pack_format` or folder name (CONTRACT §1.9).
- The **1.21 plural→singular rename** (format 48): **≤1.20.6** used `functions/`,
  `tags/functions/`; **1.21+** uses singular `function/`, `tags/function/`.
- **1.21.9+ (25w31a):** the `packmeta_shape` field is `"minmax"`, and
  `write_pack_mcmeta` **emits** `{"pack":{"min_format":N,"max_format":N,…}}` for
  those rows (a single `pack_format` is silently disabled there). `uses_minmax`
  (`:152-156`) is just `packmeta_shape=="minmax"`. So **1.21.9 is SUPPORTED**
  (dp 88 / rp 69, `confidence:"high"`) — the format is verified; only the in-game
  listen remains.

**To port within the supported band:** the row usually already exists. To add a new
MC row, give `_vrow` the dp/rp numbers from <https://minecraft.wiki/w/Pack_format>,
the right folder singular/plural, `packmeta_shape` (`single`/`minmax`), `sign_dialect`
(`component_string` <1.21.5 / `component_snbt` ≥1.21.5), `has_tick_rate`, `tier`, and
an honest `confidence`. Do **not** touch the mod for this — but DO use the two
companion CLIs: `scripts/build_resourcepack.py --mc-version <v> --samples-root <dir>`
repacks `qzpno_mv` with the version's `rp_format` + pack.mcmeta shape (a de-hardcoded
port of `poc/02e`), and `scripts/mod_build.py --mc-version <v> [--write]` prints (or
applies into `mod/redpiano/gradle.properties` + `build.gradle`) the verified mod
toolchain. `mod_build.py` does **not** run gradle and does not widen the tested
`fabric.mod.json` range — a recompiled jar still needs one in-game listen.

### 6.5 Reproducibility gap — the missing gradle wrapper (call-out + fix)

`mod/redpiano/` has **no `gradlew`/`gradlew.bat` and no `gradle/wrapper/`
directory** (confirmed: only `build.gradle`, `gradle.properties`,
`settings.gradle` exist). Consequences:

- Builds depend on a **specific local Gradle install** at a non-obvious doubled
  path (§6.3) — not reproducible on another machine / CI, and easy to get wrong.
- No pinned Gradle version → a different local Gradle may be incompatible with
  Loom 1.10.5.

**Recommended fix (future agent):** generate and commit a wrapper so the build
is self-contained and reproducible:

```bash
cd mod/redpiano
"<local gradle>/bin/gradle.bat" wrapper --gradle-version <version-supported-by-loom-1.10.5>
# commit: gradlew, gradlew.bat, gradle/wrapper/gradle-wrapper.jar, gradle/wrapper/gradle-wrapper.properties
```

Then builds become `./gradlew build` (or `gradlew.bat build`) with no external
path quirk. Pick a Gradle version Loom 1.10.5 supports (Loom 1.10 targets
Gradle 8.x; the current doubled-path install is 9.2.1, which is why the path is
unusual). Verify the wrapper builds the same jar before relying on it.

### 6.6 Verification matrix (what "it works" means)

After any port, verify **in game**, not just "it compiled":

1. **Mod loads:** log shows `[RedPiano] loaded — …` (`RedPiano.java:37`). No
   mixin `InjectionError` in the log (would mean checklist #6/#7 wrong).
2. **Mapped block plays custom sound:** put a known mapping block (e.g.
   `white_concrete` → `qzpno:pno_c1_p`) under a note block, power it; you hear
   the **piano sample**, not the vanilla note-block tone, with the right pitch.
3. **Non-mapped block unchanged:** a note block over (say) dirt still plays
   vanilla.
4. **Per-player centering:** walk away from the machine while it plays — sound
   does **not** cut out (this is the headline fix; if it cuts, checklist #11
   `playSeededSound` overload is wrong).
5. **`rpcfg` toggles:** `scoreboard players set human rpcfg 0` removes the
   jitter; `poly 0` removes chord attenuation.
6. **`stopsound` cut works:** `/stopsound @a record qzpno:pno_c1_p` silences that
   note (confirms RECORDS source, checklist #12).
7. **Resource pack:** the `qzpno` pack loads without the "incompatible
   pack_format" warning (confirms §6.4 numbers). Silence with no errors usually
   = wrong `pack_format` (MC auto-disables a mismatched pack).

### 6.7 Recommended `fabric.mod.json` version-range strategy (refuse cleanly)

Current ranges (`fabric.mod.json:15-20`):

```json
"depends": {
  "fabricloader": ">=0.16.0",
  "minecraft":    "~1.21.8",
  "java":         ">=21",
  "fabric-api":   "*"
}
```

`"minecraft": "~1.21.8"` means ">=1.21.8 <1.22" (tilde = patch range). That is a
**reasonable, conservative** policy and the recommended pattern: because the
mixin binds to internal `NoteBlock.triggerEvent` bytecode, the mod is **only
known-good on versions it was tested against**. Strategy:

- **Pin to tested versions, refuse to load otherwise.** Keep `minecraft` to a
  range you have actually verified (e.g. `~1.21.8`, or `">=1.21 <1.22"` only if
  you've smoke-tested across that span). Loader then **declines to load** the
  mod cleanly on an untested MC (a clear dependency error) instead of letting
  the mixin apply against a changed `NoteBlock` and **crashing or silently
  mis-behaving** at runtime. Refusing to load is strictly better than a runtime
  mixin failure.
- **`"fabric-api": "*"`** is loose but acceptable — only stable events
  (`ServerTickEvents`) are used. Tighten to a min build if a future API is used.
- When you port, **bump the `minecraft` range to exactly the version(s) you
  re-verified in §6.6**, never wider on faith.
- Keep `redpiano.mixins.json` `"defaultRequire": 1` so a non-applying mixin
  **fails loudly at load** rather than silently producing a sound-less mod.

- **Vestigial lang key.** `assets/redpiano/lang/en_us.json` defines
  `block.redpiano.speaker = "Piano Speaker"`, but the mod registers **no block**
  — this is a leftover from an earlier "custom speaker block" design that the
  note-block re-skin replaced. Harmless; can be deleted.
- **`version = "1.0.0"`** is hardcoded in `build.gradle:6` and injected into
  `fabric.mod.json` via `${version}` + `processResources` `expand`
  (`build.gradle:35-40`, `fabric.mod.json:4`). Bump in `build.gradle`.
- **`environment: "*"`** (`fabric.mod.json:8`) but the logic is server-side
  (`level instanceof ServerLevel` gate, `ServerPlayer`). It's a server-logic mod
  shipped to both sides (fine for singleplayer/integrated server).
- **`group`/package mismatch is fine:** `build.gradle` `group='com.redpiano'`,
  Java package `com.redpiano`, but `gen_multi_map.py` historically referenced a
  `com.example.redpiano` path in an early draft — the **live** source is
  `com/redpiano/…`; ignore any `com.example` reference.
- **The 103 count is load-bearing.** `gen_redpiano_map.py` asserts block
  uniqueness/sufficiency (`:60-61,87`); `gen_multi_map.py` only *prints* the
  total (§5.3 Known Issue #1). If you grow the map, keep both writers and the
  resource pack (`qzpno`) in sync, and re-run **both** scripts.
